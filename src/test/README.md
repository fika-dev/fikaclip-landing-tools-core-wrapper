# 코덱 매트릭스 테스트

모든 미디어 연산을 컨테이너 · 코덱 단위로 검증합니다. 실제 영상 파일과 시스템에
설치된 `ffmpeg`으로 돌아갑니다.

```
npm run test:media                                   # 전체 (354개, 약 105초)
npm run test:media:one -- 'src/test/watermark/*.test.ts'   # 연산 하나
npm run typecheck:test                               # 테스트 타입체크 (빌드 설정은 src/test 를 제외함)
```

`tsx`로 TS를 그대로 실행하므로 번들 단계가 없고, **파일 하나만 독립 실행**됩니다.

```
node --import tsx --test src/test/watermark/mp4.test.ts
```

글롭은 Node가 직접 펼치므로 셸이 필요 없습니다 — IDE 실행 구성에 그대로 넣을 수 있습니다.

```
WebStorm → Run/Debug Configurations → + → Node.js
  Working directory : lib/video-editor
  Node options      : --import tsx --test
  JavaScript file   : src/test/watermark/mp4.test.ts
```

디렉터리 전체를 돌리려면 `JavaScript file` 대신 `Application parameters`에
`'src/test/watermark/*.test.ts'` 처럼 패턴을 넣으면 됩니다. 소스를 직접 돌리므로
브레이크포인트도 TS에 그대로 걸립니다.

## 구성

```
fixtures/videos/              코덱 매트릭스용 1초 샘플 33개 + manifest.csv
fixtures/patterns/            위치·방향을 볼 수 있는 패턴 샘플 (2x2 사분면, 비율별 4개)
fixtures/multi-track/         오디오 트랙 3개 샘플 (레벨 20 dB 간격)
fixtures/manifest.test.ts     샘플이 매니페스트와 일치하는지 확인
support/
  create*UseCase.ts           연산별 유즈케이스 조립 (앱의 같은 이름 팩토리와 동일)
  createTestRuntimeConfig.ts  앱과 다른 유일한 지점 — 런타임 seam과 그 이유
  run*Case.ts                 샘플 하나를 돌리고 결과를 측정하는 실행기
  assert*.ts / probe* / decode* / FramePixels.ts   측정과 단정

```

## 이렇게 만든 이유

**동작은 전부 라이브러리의 유즈케이스로 합니다.**
연산마다 앱과 같은 이름의 팩토리가 있습니다 — `createWatermarkUseCase`,
`createVideoFormatConversionUseCase` 처럼요. 내용도 `src/video/service/<기능>/`의
팩토리와 같게 맞춰 뒀습니다. import는 패키지 엔트리(`../../index`)만 쓰고 내부 경로를
찔러보지 않습니다. 즉 테스트가 조립하는 방식이 외부 소비자가 조립하는 방식입니다.

테스트가 ffmpeg 명령을 직접 적어서 연산을 수행하면 안 됩니다. 기존
`scripts/synthetic`이 그렇게 하고 있어서 코덱 플래그가 틀려도 잡아내지 못합니다.
직접 ffmpeg을 쓰는 곳은 **측정**(ffprobe · 픽셀 · 전체 디코딩), **입력 준비**(비프음,
워터마크 이미지), 그리고 아래 런타임 seam뿐입니다. 측정은 일부러 라이브러리를 쓰지
않습니다 — 검사 대상과 검사 도구가 같으면 서로를 보증하지 못합니다.

**런타임 seam 하나만 앱과 다릅니다. 그래서 증명 범위에 한계가 있습니다.**
`createTestRuntimeConfig`가 `FfmpegRuntime` 자리에 Node용 런타임을 끼워 넣고,
리포지토리가 만든 인자 목록은 손대지 않고 시스템 `ffmpeg`에 넘깁니다. 바꿔 끼우는
이유는 선택이 아니라 제약입니다 — `FfmpegRuntime`은 `@ffmpeg/ffmpeg`을 쓰고 그쪽은
브라우저 전역 `Worker`를 요구하는데 Node에는 없습니다. `@ffmpeg/core`를 직접 띄우는
것도 `self` · `location` · `document` · `fetch` 를 전부 흉내내야 해서, 그 지점에서는
"외부에서 라이브러리를 쓴 것"이 아니라 직접 만든 가짜 브라우저 안에서 쓴 것이 됩니다.

| | |
| --- | --- |
| 증명됨 | 조립, 명령, 각 리포지토리가 만드는 인자, 그 인자가 실제 미디어에서 내는 결과 |
| 증명 안 됨 | ffmpeg.wasm 전송 계층(`FfmpegRuntime` · worker · `@ffmpeg/core`)과 DOM 기반 `BrowserMediaProbeRepository` |

두 번째 칸은 브라우저에서 돌리는 테스트가 있어야 메워집니다. Node 테스트로는
불가능하니, 그 범위를 기대하지 마세요.

**테스트는 선언된 유효 조합에서 출발합니다.**
`listSupportedOutputCombinations()`가 라이브러리가 쓸 수 있는 조합의 기준입니다.
가능한 조합을 전수로 시도하는 대신, 제공하기로 한 조합만 정확히 훑습니다.

**영상 파일은 커밋하고, 나머지는 실행 중에 만듭니다.**
샘플을 그때그때 인코딩하면 로컬 ffmpeg에 어떤 인코더가 들어 있는지에 따라 입력이
달라집니다. 그래서 샘플은 고정된 바이트로 커밋했습니다. 삽입할 비프음과 워터마크
이미지는 `lavfi`로 만들어서 입력 파일이 필요 없습니다.

**픽스처는 두 종류입니다.** 코덱 샘플(`fixtures/videos/`)은 컨테이너와 코덱을 훑기
위한 것이고, 그림은 단색 한 장입니다. 그래서 "프레임의 **어디에** 무슨 일이 생겼나"는
못 봅니다 — (0, 0)에서 자른 것과 (320, 180)에서 자른 것이 픽셀까지 똑같습니다.
패턴 샘플(`fixtures/patterns/`)은 그걸 위한 것으로, 사분면마다 다른 색이라 출력의
색이 어느 영역을 가져왔는지, 그리고 그림이 뒤집히지 않았는지 알려줍니다. 비율별로
네 개가 있어서(16:9 · 9:16 · 4:3 · 1:1) 비율 간 변환의 출발점이 됩니다. 색은 평면 블록으로 골랐습니다 —
저주파 색은 손실 압축을 거의 그대로 통과해서, H.264를 두 번 거쳐도 1~2 단위밖에
안 움직입니다.

**픽스처는 목록이 아니라 두 개의 축입니다.**
`loadCodecSampleMatrix(container)`가 `videoCodecs`와 `audioCodecs`를 따로 내주고,
`get()` · `withVideo()` · `withAudio()`로 꺼냅니다. 컨테이너 하나가 한 종류가
아니기 때문입니다 — 같은 `.mp4`에 여러 코덱 짝이 들어갑니다. 네 컨테이너 모두
두 축의 완전한 교차곱이고, 로더가 그걸 검사합니다. 한 축만 바꾸는 테스트는 그
사실이 코드에 드러납니다.

**지원하지 않는 요청은 ffmpeg 전에 거절합니다.**
`CodecCompatibilityRepository`가 변환 계획을 세우기 전에
`assertSupportedOutputRequest`로 요청을 검사합니다. 그래서 테스트는 "거절되는가"를
확인할 수 있고, 실패해도 ffmpeg 종료 코드가 아니라 대안을 알려주는 메시지가 옵니다.
일부는 ffmpeg이 실제로 만들 수 있는데도 거절합니다 — VP9-in-MP4는 표준 자리가 있고
인코딩도 되지만 Safari가 재생하지 못합니다.

**스트림 정보로 안 보이는 효과는 픽셀로 확인합니다.**
워터마크의 위치 · 크기 · 투명도는 컨테이너 · 코덱 · 해상도 · 길이를 전혀 바꾸지
않습니다. `readFramePixels`로 프레임을 직접 읽어야 구별이 됩니다. 샘플 영상이 단색
한 장이라 워터마크가 덮은 범위가 픽셀 단위로 또렷하게 드러납니다.

**소리는 짐작하지 않고 측정합니다.**
코덱 이름만 보면 빈 오디오 스트림도 통과합니다. `detectAudioLoudness`로 실제 소리가
들어왔는지 확인합니다. 손실 압축은 완전한 무음을 쓰지 않습니다 — AAC의 바닥값이
약 -91 dB이고 샘플 중 가장 조용한 소리가 약 -39 dB라서, 무음 기준은 -inf가 아니라
-60 dB 아래로 잡았습니다.

## 케이스 작성 방법

`watermark/*.test.ts`가 기준 형태입니다. mp4 · mov · mkv 세 파일은 컨테이너 이름,
MIME 타입, 설명 주석만 다르고 나머지는 같습니다. 같은 연산인데 파일마다 모양이
다르면 맞춰야 할 신호로 봅니다.

```ts
describe("<컨테이너> 컨테이너 <연산>", () => {
  // 두 축이 서로 영향을 주지 않으면 하나씩 고정하고 훑는다
  describe("오디오 코덱 축 — ...", () => { for (const s of MATRIX.withVideo("h264")) ... });
  describe("비디오 코덱 축 — ...", () => { for (const s of MATRIX.withAudio("aac")) ... });

  describe("<옵션>별 — 실제 픽셀로 검증", () => {
    let source: SampleMeasurement;
    before(async () => { source = await measureSample(PINNED_SAMPLE); });

    // 옵션 하나당 테스트 하나. 각각 다른 테스트로는 확인할 수 없는 것을 본다
    describe("현재 동작 기록: ...", () => { /* 버그는 원인을 주석에 남기고 기록 */ });
  });
});
```

아래 규칙은 실수가 잦은 순서로 적었습니다.

**1. 다른 테스트가 통과시킬 수 없는 것을 확인하세요.**
옵션을 바꿨는데 확인하는 값이 그대로면, 그 테스트는 "에러 없이 끝났다"만 보고 있는
겁니다. 워터마크의 위치 · 크기 · 투명도를 바꿔도 컨테이너 · 코덱 · 해상도 · 길이는
전부 같습니다. 그래서 이 값들만 보던 초기 버전은 세 테스트가 서로 구별되지 않았고,
워터마크를 아예 그리지 않아도 통과했습니다.

**2. 형제 테스트끼리 서로 어긋나게 만드세요.**
기본 크기(64x64) 테스트는 (56, 56)이 워터마크 색이어야 하고, 32x32 테스트는 같은
좌표가 원본 색이어야 합니다. 크기 옵션이 동작하지 않으면 둘 중 하나는 반드시
실패합니다.

**3. 원본을 먼저 재서 기준으로 쓰세요.**
"나머지는 그대로다"는 원본과 결과를 비교해야 하는 말입니다. `measureSample`이 그
용도입니다.

**4. 경계는 안쪽과 바깥쪽을 같이 확인하세요.**
사각형 안의 마지막 픽셀과 그 바로 옆 픽셀을 함께 봅니다. 한쪽만 보면 크기가
얼마든 통과합니다.

**5. 전제도 확인하세요.**
원본이 이미 그 색이면 픽셀 비교는 아무 의미가 없습니다. `assertWatermarkLayer`는
이것을 가장 먼저 확인합니다.

**6. 바뀌지 않아야 하는 것도 확인하세요.**
워터마크에서 떨어진 픽셀들, 그리고 `-c:a copy`를 쓰는 연산이면 오디오 음량까지.
복사는 재인코딩이 아니므로 음량이 비슷한 게 아니라 같아야 합니다.

**7. 두 축이 서로 영향을 주지 않으면 하나씩 훑으세요.**
비디오 코덱 3개 × 오디오 코덱 3개를 다 돌리면 9번인데, 오디오 코덱 확인을 비디오
코덱마다 반복하는 셈입니다. 한 축을 고정하고 다른 축만 훑으면 3 + 3번으로 같은
것을 확인합니다.

**8. 일부러 깨뜨려서 빨간불이 켜지는지 보세요.**
동작을 임시로 바꾼 뒤 의도한 테스트만 실패하는지 확인합니다. 투명도 테스트는 이렇게
검증했습니다 — 필터 순서를 바꿔 버그를 고치면 세 컨테이너에서 2개씩 6개가 실패하고
나머지 37개는 그대로 통과합니다.

**9. 버그는 건너뛰지 말고 현재 동작으로 적어두세요.**
원인과 고칠 방향을 주석에 남깁니다. 나중에 실제로 고쳤을 때 빨간불이 왜 켜졌는지
바로 드러납니다.

**10. 동작은 유즈케이스로, 측정은 직접 하세요.**
새 연산을 테스트할 때 리포지토리를 테스트에서 직접 호출하거나 ffmpeg 명령을 손으로
적지 마세요. `create<기능>UseCase(workDir)` 팩토리를 만들어 앱의 같은 이름 팩토리와
내용을 맞추고, 그걸로 동작시키세요. 반대로 결과 측정은 라이브러리를 쓰지 말고
ffprobe · 픽셀 · 전체 디코딩으로 직접 하세요. 라이브러리 검증에 라이브러리를 쓰면
둘이 같이 틀렸을 때 둘 다 통과합니다.

예외는 대조군입니다. `audio-addition/webm.test.ts`는 ffmpeg을 손으로 호출해서
"출력 코덱만 바꾸면 성공한다"를 보여주는데, 이건 라이브러리가 틀렸다는 것을
증명하려는 목적이므로 일부러 라이브러리를 거치지 않습니다.

### 변환 계열 연산은 세 가지를 확인합니다

`video-format-conversion/*.test.ts`가 그 형태입니다. `assertConversionOutput`이
아래 셋을 한 번에 봅니다.

1. **목표대로 바뀌었는가** — 컨테이너, 코덱, MIME 타입, 그리고 계획이 고른 모드
2. **바꾸라고 하지 않은 것은 그대로인가** — 해상도, 길이, 샘플레이트, 채널 수
3. **영상·오디오 프레임이 정상인가** — 끝까지 디코딩해서 오류가 없고, 프레임 수가
   원본과 같고, 화면이 원본과 같고, 소리가 들리고 음량이 원본과 비슷한가

세 번째가 컨테이너·코덱 이름만으로는 볼 수 없는 부분입니다. 헤더는 멀쩡한데 안쪽
패킷이 잘려 있거나, 프레임이 빠지거나, 화면이 검게 나와도 프로빙은 요청한 대로
보입니다. `decodeMediaStreams`가 전체를 디코딩해서 그걸 잡습니다.

허용치는 모드에 따라 다릅니다. 리먹싱은 스트림을 그대로 복사하므로 픽셀과 음량이
정확히 같아야 하고, 트랜스코딩은 재인코딩이므로 느슨합니다 — VP8은 libvpx 기본
품질에서 단색 배경을 채널당 최대 16까지 흔듭니다. 느슨한 허용치만으로는 검은 화면도
통과할 수 있어서, 화면이 검지 않다는 것을 따로 확인합니다.

### 화면비 변환은 "늘렸는지 채웠는지"를 봅니다

`video-aspect-ratio/*.test.ts`는 **컨테이너와 코덱을 소스 그대로 두고** 프레임만 바꿉니다.
포맷을 바꾸는 건 별개 연산이라 그쪽 테스트에서 다룹니다.

출력 프레임 크기만 보면 늘린 것과 여백을 채운 것을 구별할 수 없습니다. 둘 다 같은
크기 상자를 채우기 때문입니다. 구별되는 지점은 **그림이 어디서 끝나는가**입니다.
`assertAspectRatioFrame`이 검은 테두리에서 안쪽으로 스캔해 그림의 띠를 찾고,
그 띠가 여전히 소스의 640x360이고 가운데에 있는지를 봅니다.

- 띠 크기가 소스와 같다 → 늘리지 않았다
- 띠 시작 위치가 가운데다 → 중앙 정렬했다
- 테두리가 검다 → 여백을 검은색으로 채웠다

`AGENTS.md`가 이 연산에 대해 적어 둔 규칙("원본 비율 유지, 중앙 배치, 나머지는 검은
여백")을 픽셀로 옮긴 것입니다. `pad`를 `scale`로 바꿔 보면 여백이 생기는 모든 비율이
`picture height changed: expected the source's 360px, got 1138px` 로 실패합니다.
16:9은 여백이 아예 없어서 구별되지 않는데, 그건 당연합니다.

**비율 간 변환은 16쌍 전부를 돕니다.** 네 비율의 패턴 픽스처가 있어서 항상 16:9에서
출발하지 않고 9:16 → 4:3 처럼 실제 비율 간 변환을 테스트합니다. 이 연산은 그림을
줄이지 않으므로 9:16을 16:9로 바꾸면 위아래를 잘라내는 대신 **프레임이 옆으로
넓어집니다**(360x640 → 1138x640).

세 가지를 픽셀로 봅니다.

| 확인 | 무엇을 배제하는가 |
| --- | --- |
| 띠 크기 = 소스 크기 | 늘리기 |
| 띠 위치 = 중앙 | 한쪽으로 치우친 배치 |
| 사분면 색 순서 | 뒤집기 · 회전 |

세 번째가 없으면 뒤집힌 그림도 통과합니다 — 뒤집어도 띠 크기와 위치는 똑같기
때문입니다. 실제로 `vflip`을 끼워 보면 `top-left quadrant: expected ~rgb(255, 0, 0),
received rgb(0, 0, 255)` 로 비율 변환 케이스가 전부 빨간불이 되고, 띠 단정은 그대로
통과합니다.

**중앙이 1픽셀 어긋날 수 있습니다.** yuv420p는 2x2 블록마다 색 정보를 하나만
저장하므로 그림이 짝수 행에서만 시작할 수 있습니다. 360px 그림을 1138px 프레임에
넣으면 이상적인 중앙은 389인데 실제로는 388에 놓이고, 위 388 / 아래 390이 됩니다.
그래서 기대값은 `(프레임 - 그림) / 2`가 아니라 그걸 짝수로 내린 값입니다.

### 위치는 패턴 픽스처로 봅니다

`video-crop/mp4.test.ts`의 "자를 위치" 그룹이 그 형태입니다.

크롭의 `x` · `y`를 무시하는 구현도 단색 픽스처에서는 전부 통과합니다. 잘린 크기가
같으면 픽셀도 같기 때문입니다. 사분면 패턴에서는 이렇게 갈립니다.

| 요청 | 출력에 들어와야 하는 색 |
| --- | --- |
| (0, 0) 320x180 | 전부 좌상단 빨강 |
| (320, 180) 320x180 | 전부 우하단 노랑 |
| (160, 90) 320x180 | 네 모서리가 각각 빨강 · 초록 · 파랑 · 노랑 |

세 번째가 가장 강합니다. 사분면 경계를 걸쳐 자르므로 출력의 모서리마다 다른 색이
오고, `x`나 `y` 중 하나만 틀려도 모서리 색이 바뀝니다. 실제로 `x`·`y`를 0으로
고정해 보면 두 번째와 세 번째만 빨간불이 되고 첫 번째는 통과합니다 — 첫 번째는
원래 (0, 0)을 요청했으니 맞습니다.

위치는 컨테이너와 무관하므로 이 그룹은 한 파일에만 둡니다.

### 구간 볼륨은 구간별로 측정합니다

`audio-volume/*.test.ts`가 그 형태입니다. 포맷별 파일 안에서 그 포맷이 담을 수 있는
오디오 코덱을 훑고, 요청한 구간만 요청한 배율로 바뀌었는지 봅니다.

파일 전체 평균 음량으로는 두 주장 중 **어느 것도** 표현할 수 없습니다. 필터가 엉뚱한
구간에 걸렸거나 트랙 전체에 걸렸어도 전체 평균은 어차피 움직입니다. 그래서 조절한
구간과 **건드리지 않은 구간**을 따로 재서, 각각을 원본의 같은 구간과 비교합니다.

배율은 데시벨로 환산해 비교합니다 — `20 × log10(배율)`.

| 요청 | 기대 | 실측 |
| --- | --- | --- |
| 0% | 무음 | -91 dB (인코더 바닥) |
| 50% | -6.02 dB | -6.00 |
| 100% | 0 dB | 0.00 |
| 150% | +3.52 dB | +3.50 |
| 200% | +6.02 dB | +6.00 |

건드리지 않은 구간은 다섯 경우 모두 0.00 dB였습니다. 구간 조건(`enable=between`)을
제거해 트랙 전체에 걸리게 만들어 보면 "건드리지 않음" 단정이
`expected 0.00 dB for volume 1, measured -6.00 dB` 로 전부 빨간불이 됩니다.

**측정 창은 구간 경계에서 떨어뜨려야 합니다.** AAC 프레임은 1024 샘플(약 21ms)이고,
필터 전환점도 `-ss`/`-t` 자르는 지점도 프레임 경계에 맞지 않습니다. 경계에 붙여
재면 반대쪽 샘플이 섞여서 50%가 -5.0 dB로, 무음이 -50 dB로 읽힙니다. 안쪽으로
0.05~0.1초 당기면 이론값과 0.02 dB 안에서 맞습니다.

### 추출물은 "재생되는 상태인지"를 봅니다

`audio-extraction/*.test.ts`가 그 형태입니다. 소스 컨테이너별 파일 안에서 추출 가능한
음성 포맷(mp3 · m4a · ogg)을 훑고, 나온 파일이 실제로 열리는 상태인지 확인합니다.

코덱 이름과 "소리가 들린다"만으로는 부족합니다. 프로빙은 헤더만 읽으니, 헤더는
멀쩡한데 안쪽 패킷이 잘못 들어 있는 파일도 정상으로 보입니다. `.wav` 추출물이 정확히
그렇습니다 — 프로브는 통과하고 재생은 안 됩니다. `assertExtractedAudioPlays`가 두 가지를
같이 봅니다.

| 확인 | 무엇을 배제하는가 |
| --- | --- |
| 전체 디코딩 오류 0, 종료 코드 0 | 헤더만 맞는 깨진 파일 |
| 길이 · 샘플레이트 · 채널 수 = 원본 | 잘린 추출, 리샘플, 채널 손실 |
| 음량 = 원본 ±1 dB | 엉뚱한 레벨로 나온 추출 |
| 비디오 스트림 0 | `-vn` 누락 |

실측값입니다 — mp3는 LAME 때문에 원본보다 0.5 dB 낮고, m4a(aac)와 ogg(opus)는 레벨이
같습니다. 길이는 인코더 패딩 때문에 1.000~1.009초로 흔들립니다.

`.wav` 케이스는 이 장치의 음성 검증 역할도 합니다 — 디코딩 오류가 **있어야** 통과하므로,
디코딩 검사가 고장나면 그 테스트가 먼저 깨집니다. 반대쪽은 추출에 `-ar 24000`을 끼워
보면 `sample rate is preserved` 로 전부 빨간불이 됩니다.

## 연산별로 스트림을 어떻게 다루는가

테스트 결과를 해석할 때 가장 먼저 볼 표입니다.

| 연산 | 영상 | 소리 | 코덱 지정 가능? |
| --- | --- | --- | --- |
| add-audio | `-c:v copy` | AAC로 재인코딩 | 불가 |
| adjust-volume | `-c:v copy` | AAC로 재인코딩 | 불가 |
| mute (전체) | `-c:v copy` | `-an`, 스트림 제거 | 불가 |
| mute (구간) | `-c:v copy` | AAC로 재인코딩 | 불가 |
| extract-audio | `-vn`, 스트림 제거 | 재인코딩, 포맷별 기본 코덱 | 일부 |
| crop | 재인코딩, 기본 H.264 | 재인코딩, 기본 AAC | **가능** |
| watermark | 재인코딩, H.264 고정 | `-c:a copy` | 불가 |
| aspect-ratio | 재인코딩, 인자로 필수 | 인자로 필수 | **가능** |
| 포맷 변환 | 계획에 따름 | 계획에 따름 | **가능** |

`-c:a copy`와 `-c copy`만이 라이브러리가 인코딩할 수 없는 코덱을 지켜냅니다. 그래서
워터마크는 PCM과 FLAC을 그대로 두는데, 나머지 연산은 전부 변환해 버립니다.

## 컨테이너 규칙

| 컨테이너 | 영상 출력 | 소리 출력 | 이유 |
| --- | --- | --- | --- |
| MP4 | H.264, H.265 | AAC, MP3, Opus | 어디서나 재생되도록 좁힌 선택. VP9도 담기지만 Safari가 못 읽음 |
| MOV | H.264, H.265 | AAC, MP3 | MP4와 같은 이유. Opus는 QuickTime에 표준 자리가 없음 |
| MKV | 위의 전부 | 위의 전부 | 코덱을 가리지 않음 — 코덱 ID와 설정값만 저장 |
| WebM | VP8, VP9 | Opus | 브라우저용으로 일부러 좁혀 놓은 Matroska |

테스트가 기대고 있는 사실들:

- ffprobe는 `.mkv`와 `.webm`을 모두 `matroska,webm`으로 보고합니다. 둘을 가르는 건 확장자뿐입니다.
- 파일을 **쓸 때는 확장자**가, **읽을 때는 파일 내용**이 포맷을 결정합니다. 그래서 삽입할 트랙 이름을 `<name>.<index>.input`으로 바꿔도 ffmpeg이 읽습니다.
- 확장자가 먹서를 고르고, 같은 계열 먹서끼리도 규칙이 다릅니다. `.m4a`는 코덱을 제한하는 `ipod` 먹서라 MP3를 거부하고, `.mp4`는 `mp4` 먹서라 받습니다.
- ffprobe는 `h265`를 `hevc`로, `pcm`을 `pcm_s16le`로 부릅니다.
- `lavfi`의 `sine`은 모노로 나오고, ffmpeg 기본 `vorbis` 인코더는 스테레오만 받습니다.
- 크롭 크기는 짝수로 내려갑니다. yuv420p가 2x2 블록마다 색 정보를 하나만 저장하기 때문입니다.
- yuv420p 때문에 패딩 오프셋도 짝수여야 합니다. 홀수 중앙이 필요한 비율은 1픽셀 위로 치우칩니다.
- `-preset veryfast`는 x264/x265 전용 옵션입니다. libvpx에서는 경고만 나고 넘어가므로 WebM 화면비 변환도 성공합니다.
- 컨테이너가 받아들이는 것과 제공하기로 한 것은 다릅니다. VP9-in-MP4와 MP3-in-MOV는 ffmpeg이 만들어내지만, 앞쪽은 재생 호환성 때문에 제공하지 않습니다.
- `ffprobe -count_frames`의 `csv=p=0` 출력에는 구분자가 하나 더 붙습니다. 숫자만 뽑아 써야 합니다.

## 이 테스트들이 기록한 문제

아래는 **현재 그렇게 동작한다**고 단정해 둔 버그입니다. 고치면 해당 테스트가
실패하는데, 그 빨간불이 "고쳐졌다"는 신호입니다. 그때 단정을 성공 쪽으로
바꿔 주세요.

1. **소리 관련 연산들이 출력 컨테이너를 보지 않습니다.** `add-audio`, `adjust-volume`,
   구간 `mute`가 `-c:a aac`를 박아 두고 있어서 WebM 입력은 전부 헤더 쓰기 단계에서
   실패합니다. `audio-addition/webm.test.ts`에 대조 케이스를 뒀습니다 — 같은 원본,
   같은 비프음, 같은 필터로 `-c:a libopus`만 쓰면 성공합니다. 필요한 컨테이너별
   기본값은 `CodecCompatibilityRepository`가 이미 알고 있습니다
   (`output-support/codecCompatibility.test.ts` 참고).
2. **크롭의 기본값도 컨테이너를 보지 않습니다.** 더 나쁜 쪽인데, `-c:v libx264`와
   `-c:a aac`라서 영상과 소리가 둘 다 WebM 규칙을 벗어납니다. VP8/VP9와 Opus를
   넘기면 성공하므로, 고칠 부분은 기능이 아니라 기본값입니다.
3. **워터마크는 WebM에서 쓸 방법이 아예 없습니다.** `-c:v libx264`가 바꿀 수 없게
   고정돼 있습니다. 명령에 출력 코덱 항목을 추가해야 합니다.
4. **`add-audio`가 원본 소리를 섞지 않고 교체합니다.** `buildMixFilter`가 새로 넣는
   트랙만 `amix`에 넣고, `0:v?`와 `[mixed]`만 매핑합니다. 컨테이너별 파일마다
   볼륨 0인 비프음을 넣어 결과가 무음인지로 확인합니다.
5. **`extract-audio`의 `.wav` 결과물은 재생이 안 됩니다.** 포맷별 기본 코덱이
   `.mp3`와 `.ogg`를 뺀 전부를 AAC로 고르기 때문에 WAV에 AAC가 담깁니다. 먹싱은
   되고 프로빙도 통과하지만, 끝까지 디코딩하면 오류가 17~25줄 나오고 음량 측정조차
   안 됩니다. 올바른 선택지도 없습니다 — `AudioCodec`에 PCM이 아예 없어서 이 포맷을
   제대로 요청할 방법이 없습니다.
6. **워터마크 투명도가 전혀 적용되지 않습니다.** 워터마크 이미지에 알파 채널이
   없는데 필터가 `colorchannelmixer=aa=<투명도>`를 `format=rgba`보다 먼저
   실행합니다. 아직 없는 채널을 줄이니 아무 일도 안 일어나고, 그 다음
   `format=rgba`가 불투명한 알파를 붙입니다. 그래서 `opacity: 0`을 줘도 진하게
   그려집니다. 두 단계의 순서만 바꾸면 고쳐집니다 — 실제로 바꿔 보면 세 컨테이너에서
   2개씩 6개가 실패하고 나머지 워터마크 테스트는 그대로 통과합니다.
7. **볼륨 조절은 오디오 트랙을 하나만 다룹니다.** 명령에 트랙을 고르는 항목이 없고,
   리포지토리가 `-map` 없이 `-af`만 넘기므로 ffmpeg 기본 선택이 트랙 하나를 골라
   조절하고 나머지는 버립니다. 트랙 3개를 넣으면 **1개만 남습니다**(첫 트랙).
   "세 트랙 중 두 번째만 조절"은 지금 표현할 방법이 없고, 명령에 트랙 항목을 추가하고
   `-map`을 명시해야 합니다. `audio-volume/mp4.test.ts`가 레벨 20 dB 간격의 3트랙
   픽스처로 이 동작을 기록합니다.
8. **크롭의 `output.format`이 반만 반영됩니다.** 출력 경로는 입력 파일 이름의
   확장자에서 나오는데 MIME 타입은 `output.format`을 따릅니다. 그래서 다른
   컨테이너를 요청하면 원래 컨테이너 파일에 요청한 이름표가 붙습니다.
   `video-aspect-ratio`는 이 부분이 올바릅니다.
